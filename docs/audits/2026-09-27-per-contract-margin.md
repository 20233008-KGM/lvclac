## 1. 기준 수학과 적용 범위

`E`는 현재가 `C` 시점의 계좌평가금액, `N`은 보유 계약수, `K`는 가격 1단위당 1계약 손익, `m`은 계약당 유지증거금, `i`는 계약당 개시증거금이다. 모든 금액과 `K`는 동일 결제 통화여야 한다. 방향 부호 `s`는 롱 +1, 숏 -1이다.

| 항목 | 기준식 |
| --- | --- |
| 총 유지증거금 | `N × m` |
| 총 개시증거금 | `N × i` |
| 가격 P의 평가금액 | `E + s × (P − C) × N × K` |
| 유지증거금 여유 | `E − N × m` |
| 가용증거금 | `E − N × i` |
| 롱 청산 임계가 | `C − (E − N × m)/(N × K)` |
| 숏 청산 임계가 | `C + (E − N × m)/(N × K)` |
| 현재가에서 추가 주문 한도 | `max(0, floor((E − N × i)/i))` |
| 현재가 기준 명목가치·레버리지 | `C × N × K`, `(C × N × K)/E` |
| 보유 포지션의 1틱 손익 크기 | `tickSize × N × K` |

계좌평가금에 미실현손익이 이미 포함되므로 진입가부터 현재가까지의 손익을 다시 더하면 안 된다. 개시증거금은 비용이 아니므로 주문 시 계좌평가금에서 차감하지 않고 가용증거금에서만 차감한다. 현재가 `C`에서 체결가 `F`로 추가/축소 `d`계약을 가정할 때는 `E' = E + s × (C − F) × d × K`, `N' = N + d`이다. 감사 테스트는 이 식을 그대로 복사하는 대신 **현금 + 실현손익 + 잔여 미실현손익** 장부로 주문 후 평가금액을 검산했다.

예시(실제 거래소 증거금 공시값이 아닌 검산 가정): `E=27,000`, `C=75`, `N=2`, `K=1,000`, `m=6,000`, `i=9,000`. 유지 총액 12,000, 개시 총액 18,000, 유지 여유 15,000, 가용 9,000, 롱 임계가 67.5, 숏 임계가 82.5, 현재가 추가 한도 1계약이다.

청산식은 **계좌평가금이 유지증거금에 도달하는 이론적 경계**다. 거래소의 마진콜, 브로커의 강제정리 시점·체결가격을 동일하다고 보장하는 식은 아니다. CME도 개시·유지증거금을 구분하고, 유지 기준 미달 시 개시 기준까지 보충하는 마진콜을 설명한다. 증거금 규정은 상품·변동성·시점에 따라 바뀐다. 여기의 “고정”은 해당 계산 시나리오에서 고정이라는 의미다. [CME 증거금 FAQ](https://www.cmegroup.com/solutions/risk-management/performance-bonds-margins/faq-performance-bonds-margins.html)

### F1 · P1 — 소수 가격·금액을 다른 숫자로 바꾸며 작은 틱도 소실

- 위치: `src/components/InputPanel.tsx:37`, `:309`, `:460`, `src/components/NumberStepper.tsx:441`, `src/components/ResultPanel.tsx:658`, `src/utils/inputFormat.ts:75`, `:166`.
- 가격·진입가·계약당 증거금은 정수 전용 입력이다. 소수점 입력을 거부하는 대신 숫자가 아닌 문자를 제거해서 `75.25 → 7,525`로 만든다. 금액 `6,000.50`도 같은 경로다.
- 소수 허용 필드인 틱·승수도 소수 둘째 자리로 정규화한다. `0.001 → 0`, `0.0025 → 0`이 된다.
- **로컬 Chrome 실화면 재현:** 계약당 모드에서 약정가격과 현재가에 `75.25` 입력 → 둘 다 `7,525`; 틱 `0.001` 입력 후 포커스 이동 → `0`.
- 해외선물 가격의 정상적인 소수 입력을 지원하지 못하는 P1 문제다. WTI는 0.01, E-mini S&P 500은 0.25 틱을 사용한다. [CME 틱 설명](https://www.cmegroup.com/education/courses/introduction-to-futures/tick-movements-understanding-how-they-work)
- 수정 방향: 가격/통화 금액/계약수의 입력 정책을 분리하고 가격·틱의 유효 소수를 보존한다. 스테퍼·드래그·직접 입력·blur·복원 모두 같은 정책을 적용한다.

### F3 · P1 — 방향 전환 손익 단위가 틀리고 결과별 계좌금액도 다름

- 방향 전환 보정은 손익에 `K` 대신 `진입가 × K / 현재가`를 곱한다. 고정 선물승수의 단위와 불일치한다.

- 청산식만 보정 평가금액을 쓰고, 증거금 여유·레버리지·한도는 원래 입력27,000을 쓴다. 청산가가 현재가보다 아래여서 이미 위험한 숏인데 유지증거금 여유는 **+15,000**, 추가 매도 한도는 **1**로 나온다.
- **로컬 Chrome 실화면 재현:** 숏 청산가 **73**, 현재가 **75**, 유지 여유 **15,000**, 추가 매도 한도 **1** 동시 표시.
- 수정 방향: 방향 전환 시 현금 보존 시뮬레이션을 할지 입력 평가금액을 유지할지 일관된 정책으로 결정하고, 모든 결과와 주문·MTM이 같은 평가금액을 사용하게 한다. 현금 보존 정책이면 손익 승수는 항상 `K`다. 어느 정책이든 현재의 결과 간 모순은 오류다.

### F6 · P1, 인접 모드 — 총액에서 “계약당 고정”을 골라도 청산식은 비례식

- 위치: `src/calc/margins.ts:51`, `src/calc/liquidation/common.ts:98`, `src/calc/leverage.ts:270`.
- `totalMarginKind='fixed'`는 주문 후 총액 재계산에만 반영되고, 청산식 고정 여부는 `marginInputMode==='perContract'`만 검사한다.

- 수정 방향: 유지증거금의 가격 민감도 판정을 통일하고 총액·고정↔계약당의 동치성을 회귀 검증한다. 총액 모드의 미리보기·확정에서 총액 전달도 함께 확인해야 한다.

### F8 · P3 — 주문 수량 내림 보정이 실제 부족액도 무시

## 4. 모델 한계 및 수정 순서

현재 구현은 양의 현재가·양의 청산가만 반환한다. 0 이하 가격에서도 거래될 수 있는 상품까지 일반적으로 보장하지 않는다. 롱 임계가가0 이하이면 `null`이 되므로 이를 “절대 청산되지 않음”으로 읽으면 안 된다. 계좌·증거금과 손익승수의 통화가 다르면 환산이 필요하며 자동 FX 변환은 없다. 복수 종목·스프레드 상계·수수료·증거금 규정 변경·강제청산 체결 슬리피지는 본 모델 밖이다. 이러한 한계는 위 구현 오류들과 구분한다.

유지증거금만 있어도 청산식 자체는 풀 수 있지만 현재 UI/엔진은 개시증거금도 있어야 전체 계산을 시작한다. 계약승수 미입력은1로 계산한다. 두 동작은 명시된 현재 입력 계약으로 기록했으며 이번에 결함으로 추가 집계하지 않았다.

권장 수정 순서: **F1/F2 입력·표시 정밀도 → F3 동일 평가금액·승수 → F5 잘못된 상태 확정 차단 → F4/F6 주문·모드 동치 → F7/F8 지표·수치 경계**. 수정 이후 계약당 및 비율/총액 공통 경로를 재검증하고, 별도 배포 검증으로 운영 반영을 확인해야 한다. 이번 감사에서는 그 수정이나 배포를 수행하지 않았다.
